# Open Notebook 口语导演层复用设计

## 1. 目标

在现有“声音导演”macOS 桌面应用中增加一个完全离线、默认简单的口语导演层。它在语音生成前把知识文章整理成适合自然说话的普通话口语稿，再交给此前听感更稳定的 E 自然人声路线生成。

本轮不继续通过“开心、愤怒、悲伤”等情绪指令要求语音模型表演。当前 CosyVoice 情绪路线保留为研发材料，但从正式默认生成和普通用户界面撤下。

成功标准：

1. 用户只需粘贴原文、选择音色并生成，主流程不增加必填项。
2. 原文永久保留；口语稿与原文分开保存，任何失败都能退回逐字朗读。
3. 口语化不得改变数字、人名、专业词、事实、立场和结论，不得补充原文没有的事实。
4. 同一篇内容的“自然口语版”经用户试听后，应比“原文直读版”更少朗诵腔、播音腔和刻意表演感。
5. 全流程默认离线，不升级 macOS，不安装或修改系统组件。

## 2. 上游来源与许可证

选择性复用以下 MIT 许可项目：

- `lfnovo/open-notebook`，评审提交：`a7de90d38aaf18ee85fd661854d35c11e44613e2`
- `lfnovo/podcast-creator`，评审提交：`904da36cca12846e8c610fff5cab2972735b007d`

复用范围：

- 提纲、对话、说话人和节目配置的数据边界。
- “内容 → 提纲 → 口语稿 → 逐句 TTS → 合成音频”的分阶段工作流。
- 提纲和口语稿提示词的组织思路。
- 每条说话内容独立生成、保存和重试的任务结构。

不复用：

- Docker、FastAPI、Next.js、SurrealDB 和网页部署结构。
- Open Notebook 的账号、密钥、云端服务商管理界面。
- 默认 ElevenLabs、OpenAI、Google TTS 配置。
- Speaches/Kokoro 英文预设音色路线。
- MoviePy 直接连接 MP3 的音频合成实现。

若移植或实质改写上游代码、提示词或配置结构，项目中必须加入对应 MIT LICENSE 和来源说明，标明上游项目、提交号和本地修改。没有实质复制的纯架构借鉴也在 NOTICE 中记录来源，避免后续无法追溯。

## 3. 方案取舍

### 3.1 推荐：选择性移植到现有 Swift 架构

把上游最有价值的领域模型和工作流移植成小型 Swift 模块，继续使用现有项目存储、生成队列、播放器和三格式导出。

优点：原生桌面体验不变；没有 Docker 和数据库负担；可以复用现有分段缓存、恢复与音频整理能力；依赖边界清楚。

代价：需要把少量 Python 数据结构和提示词逻辑改写成 Swift，不能直接运行上游整套应用。

### 3.2 不采用：把 Open Notebook 作为本地服务整体嵌入

该方案可以少写部分业务代码，但会引入容器、Web 服务、数据库、端口、后台常驻进程和多套配置。它不解决普通话个人音色自然度，反而明显增加安装体积、内存占用和故障面，不符合 M1 8GB/16GB 与非技术用户目标。

### 3.3 不采用：直接嵌入 `podcast-creator` Python 包

该包的核心 TTS 仍由外部服务商或 OpenAI-compatible 服务提供，并带入 LangGraph、MoviePy、Esperanto 等依赖。它适合作为参考实现，不适合作为当前桌面应用的正式运行核心。

## 4. 用户流程

### 4.1 默认流程

1. 用户选择音色并粘贴原文。
2. 应用默认采用“自然讲解”，在本机整理口语稿。
3. 应用自动生成各语音片段并制作最终 WAV、M4A 和 MP3。
4. 用户可以播放、暂停、停止、调速或在访达中查看成品。

主界面只增加一句低干扰说明：“会整理成自然口语，原文始终保留。”不要求用户先阅读或批准口语稿。

### 4.2 高级入口

以下内容放在默认折叠的高级编辑中：

- 生成方式：自然讲解（默认）／逐字朗读。
- 查看口语稿与对应原文。
- 修改单段口语稿。
- 把单段恢复为原文。
- 重新整理或只重做一段音频。

普通用户不看到模型名称、提示词、温度、种子、内存档位或上游项目术语。

### 4.3 后续双人模式

双人访谈属于第二阶段。只有单人口语稿通过听感验收后才加入“单人讲解／双人对谈”选择。双人模式可以使用两个不同音色和提问／解释角色，但不会成为首次使用的额外步骤。

## 5. 数据模型

项目格式升级到新版本，同时保留旧项目可读性。

`NarrationProject` 增加：

- `scriptMode`：`spoken` 或 `verbatim`。
- `scriptVersion`：口语导演规则、提示词或本地模型版本。
- `outline`：结构化提纲，可为空。
- `scriptState`：等待、整理中、完成、失败或回退。

`NarrationSegment` 明确区分：

- `sourceText`：对应原文片段，只读保存。
- `spokenText`：实际交给 TTS 的口语稿。
- `speakerRole`：第一阶段固定为讲解者，第二阶段可扩展。
- `scriptFingerprint`：来源、口语稿和导演版本的组合指纹。
- 现有语速、停顿、候选音频和生成状态继续保留。

旧项目迁移时，将现有 `text` 同时作为 `sourceText` 和 `spokenText`，保持已有候选音频与成品可用，不强制重新生成。

原文、口语稿、提纲、单段音频和最终成品仍保存在项目自己的本地目录。路径只保存相对值，继续执行现有目录逃逸检查。

## 6. 模块与数据流

### 6.1 `SpokenScriptDirector`

统一协议，输入原文、语言、模式和保真约束，输出提纲与口语段落。界面和项目存储不依赖具体实现。

首轮包含两个候选：

1. `RuleSpokenScriptDirector`：完全离线的保守基线，负责断句、列表口语化、标点和短句整理，不自由补写内容。
2. `LocalModelSpokenScriptDirector`：使用经单独基准验证的小型本地中文模型完成提纲和口语稿。模型只在整理阶段加载；完成后退出，再启动 TTS，避免两套模型同时占用内存。

只有本地模型在事实保真、听感和内存上均优于规则基线时才进入便携应用。模型选择不暴露给普通用户。

### 6.2 `SpokenScriptValidator`

执行确定性检查：

- 原文中的数字、百分比、日期、英文缩写和可识别专有词不得消失或改变。
- 口语稿不能为空，单段控制在约 20～55 个汉字，必要时允许专有名词导致的小幅超限。
- 禁止模型输出角色说明、舞台指令、Markdown 标题、情绪标签和“哈哈／嗯嗯”等刻意填充词。
- 无法验证时不冒险使用改写结果，回退到原文直读。

确定性检查不能证明全部事实一致，因此本地模型提示词同时要求只改表达、不增删事实；测试语料覆盖数字、人名、否定关系和结论反转。

### 6.3 `NarrationDirector`

现有分段器保留，职责调整为把已确认的口语稿转换成 TTS 片段，并为停顿和稳定 ID 赋值。它不再同时承担文章改写。

### 6.4 `SpeechEngine`

正式默认重新使用 E 对应的 `QwenSpeechEngine` 自然人声路线。TTS 只接收口语文字，不接收“愤怒、开心”等表演指令。

当前 `LocalExpressiveSpeechEngine` 和 CosyVoice 模型不再参与正式自动路由。实验代码与试听结果可以保留在研发目录，便携应用默认不再打包该模型，从而降低体积和首次准备时间。

### 6.5 `GenerationQueue` 与 `AudioAssembler`

继续复用现有能力：

- 每段单独生成、校验、保存和重试。
- 修改一段只让对应片段失效。
- 暂停后保留已完成片段。
- 统一音量、保持音高变速、淡入淡出和可控停顿。
- 导出标准 WAV、M4A 和 MP3。

不采用 Open Notebook 的 MoviePy MP3 直接串接方案。

## 7. 口语稿约束

口语导演优先改变“怎么说”，不改变“说什么”：

- 一句话只表达一个主要意思。
- 把书面长句拆开，保留原有逻辑关系。
- 列表改为“第一、第二”或自然过渡，但不新增条目。
- 允许少量“先看”“换句话说”“这里要注意”等连接词，不连续堆叠。
- 禁止广告腔、主持腔、鸡汤式总结和夸张反问。
- 不自动添加笑声、叹气、语气词和情绪表演。
- 专业词、英文缩写和数字优先原样保留；读音修正继续由高级编辑处理。

## 8. 状态、失败与恢复

- 整理口语稿和生成音频是两个独立阶段，各自保存状态。
- 口语整理失败、超时或未通过保真检查时，项目自动切换到逐字朗读并给出简短说明。
- 原文永远不被口语稿覆盖。
- 口语稿完成后立刻持久化，应用退出后可以继续生成音频。
- 音频失败沿用现有最多两次单段尝试；口语整理不进行会产生多个不同稿件的隐式重试。
- 用户主动“重新整理”时产生新稿，但旧稿和已完成音频在新稿通过验证前不删除。

## 9. 性能与设备策略

- 口语整理与 TTS 串行运行，避免内存峰值叠加。
- 规则基线必须可在 8GB 设备运行。
- 小型本地文字模型在 32GB 开发机上的限制测试只能用于发现明显问题，不能替代真实 M1 8GB/16GB 结论。
- 正式标注支持前，在真实设备完成 3000 字整理、完整生成、暂停恢复和连续播放测试。
- 如果本地文字模型不满足低配要求，正式应用仍可使用规则基线；不会自动上传原文到云端。

## 10. 验收与测试

### 10.1 功能测试

- 旧项目迁移后原音频继续可播。
- 自然讲解与逐字朗读可以切换，原文不变。
- 修改单段口语稿只重做对应音频。
- 口语整理失败可以无损回退。
- 重启应用能恢复提纲、口语稿、片段和进度。
- WAV、M4A 和 MP3 在未安装应用的设备上可播放。

### 10.2 保真测试

固定语料覆盖：

- 人名、地名、产品名和中英文混合术语。
- 金额、百分比、日期、版本号和编号列表。
- 否定句、条件句、因果关系和相反观点。
- 标题、定义、例子、结论与长句。

任何关键实体或关系改变都判定失败并回退。

### 10.3 听感验收

使用同一音色、同一 TTS 路线和相近片段长度生成：

1. 原文直读版。
2. 规则口语版。
3. 本地模型口语版（候选通过资源检查时）。

不显示内部模型名称，由用户判断哪一版最不做作、最像正常说话。口语版只有在用户明确优于原文直读后才能成为正式默认。

### 10.4 隐私与打包

- 断网状态完成口语整理和 TTS。
- 应用包不包含用户录音、原文、项目 JSON、绝对开发路径或密钥。
- 不写系统目录，不请求管理员权限，不安装 Homebrew、Docker 或系统 Python。
- 便携应用包含实际采用的许可证和来源说明。

## 11. 非目标

本轮不实现：

- 情绪表演菜单。
- 多人播客和复杂人物编辑器。
- 云端文字改写或云端 TTS。
- RAG、资料问答、引用系统和完整 NotebookLM 克隆。
- PDF、视频、网页抓取与语音转写；这些属于口语导演通过验收后的下一阶段。
- 把 Open Notebook 整仓作为产品运行依赖。
